# OPT-1660 production side-effect inventory

Status: in progress for [OPT-1660](https://linear.app/boostnlvp/issue/OPT-1660). This inventory describes the `origin/main` checkout at `74b5ad1cc`. It names the current authority or an explicit exception; it does not migrate a caller or change product policy. An owner named in the target architecture is not evidence that the current caller is routed through it.

## Scope and review method

The review covers the Rust production crates under `crates/`: profile and source/global SQLite writes, journal and capacity persistence, filesystem mutation, cache/artifact publication, scanner/watch observations that can feed durable writes, and UI/recording effects. It excludes `#[cfg(test)]` modules, `tests.rs`, `*_tests.rs`, fixture modules, build scripts, and developer tools from production claims. Inline tests in otherwise production files must be excluded at their `#[cfg(test)] mod tests` boundary; a raw `rg` count alone includes fixtures. The source SQL and file ownership rules come from [SOURCE_WRITER_CONTRACT.md](SOURCE_WRITER_CONTRACT.md), [FILE_OPERATION_OWNER_CONTRACT.md](FILE_OPERATION_OWNER_CONTRACT.md), and the owner table in [IO_ARCHITECTURE_TARGET.md](IO_ARCHITECTURE_TARGET.md).

The first scan searched all `.rs` files under `crates/` for direct filesystem creation, write, rename, removal, and `OpenOptions` calls and SQLite opens and `execute`/transaction calls; owner/queue entrypoints were inspected separately. After excluding every path segment containing `test` or `fixture`, `overrides.rs`, and trailing `#[cfg(test)] mod tests` bodies, the direct-call lexical pass found 63 candidate files: 52 in `wavecrate-library`, 6 in `wavecrate-analysis`, 3 in `wavecrate-scan`, 1 in `wavecrate-media`, and 1 in `reson`. This replaces the earlier 67-file heuristic count. A broader lexical pass also searched `tempfile`, `write_all`, `hound`, `cap_std`, SQLite transaction/execute APIs, platform clipboard/drag calls, and read-side `fs::`/`File::` use. With the same path exclusions, it found 146 candidate files: 9 profile/bootstrap, 15 journal/capacity, 1 file owner, 55 source database/readiness, 9 global database, 3 identity/SQLite utility, 12 scan/catalog/watch, 11 analysis/artifact, 17 media/recording, 13 UI/platform, and 1 design/theme. Every candidate path fits a class below, but grouping by module prefix is only a coverage aid; it cannot prove that every matching call is safe or that an indirect effect is absent. The broader pass found additional read-only paths, caller-owned WAV sinks, ANN temporary unpack files, and inline test setup in otherwise production files. The trailing-module truncation does not exclude every inline `#[cfg(test)]` item; hits such as `wavecrate-analysis/src/app_dirs.rs::TEST_CONFIG_BASE` must be classified by their actual call conditions. The scan also finds arbitrary `.execute()` methods, and separate SQL `execute_batch`/temp-table, CPAL, extension-load, network, and process-launch searches were needed to identify effects outside its first regex. Each row below names the checked path and whether it is an implemented route, a maintenance boundary, or an unresolved legacy exception.

## Observed admission and fail-closed edges

- `FileOperationOwner::submit` is the typed effect entrypoint; command families without a qualified adapter can return `EffectOutcome::Unsupported`. Its root registration is not a write grant. The source-local `recovery_io` path and startup maintenance remain separate exceptions.
- Catalog's `curation::execute_inner` validates the retained `WritableProfileGuard`, `SourceDatabase` binding, source generation, root identity, and expected revision, then calls `SourceDatabase::commit_curation_with_profile_guard`. `rating_decay::execute_inner` revalidates its page and delegates its nonempty update set to that same curation path. These checks protect the legacy caller but do not issue a `SourceWriter` command identity.
- `CatalogScanWriter::try_lock` checks cancellation and retained authority before scan phases, but its guard type is `()`. Exported `UncoordinatedScanWriter` also has a `()` guard and assumes external serialization or a SQLite transaction. Scan code calls `SourceDatabase::write_batch` directly and `scan_diff` mutates the passed batch. Catalog registration recovery separately calls `discard_source_directory_truth_generation_batch` and `cleanup_source_directory_truth` through `try_lock_cleanup`. These legacy boundaries do not issue durable typed source-writer receipts.
- `SourceDatabase::readiness_store` lends a mutating store only after retained profile/database validation; `ReadinessStore::new` on a raw connection cannot mutate in normal builds. The retained store still does not pass through a typed source-writer queue.
- In the GPUI application crates, catalog holds the production `SourceDatabase`: `lib.rs` opens/retargets it and runs directory-truth recovery; `curation.rs` and `rating_decay.rs` provide metadata mutation; `tags.rs`, `display_labels.rs`, and `wav_metadata.rs` issue revision-fenced reads; the scan crate receives `&SourceDatabase` for manifest/hash/index batches. The scan found no `readiness_store` application call and no application call to the exported similarity/ANN mutation helpers. API availability is still an unresolved route, not proof that future callers are fenced.
- Source path-only writable role aliases and global path-only `library::{load,save,open_connection}` return `ProfileOwnershipRequired` in normal builds. This is a concrete fail-closed boundary, not a substitute for migrating owner-held production callers.
- Tag-filter and tag-page queries stage bounded connection-local temp rows with `temp_store=MEMORY`, check cancellation/revision, and roll back their transaction. This is a SQL side effect without a durable source-revision advance. Filesystem observers, theme loaders, and native drag/clipboard effects never mint journal, file-owner, source-writer, or global-writer authority from the path or observation they carry.
